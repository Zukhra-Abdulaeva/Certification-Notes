# 🛡️ DAY 1 — SECURITY FUNDAMENTALS DAY

## 1 — Security: Security Fundamentals

**Theory:** Bedeutung von IT-Security, Schutz von Systemen, Daten und Services sowie grundlegende Security-Prinzipien.
**Context / Why:** IT-Systeme sind permanent Risiken ausgesetzt. Security schützt Vertraulichkeit, Integrität, Verfügbarkeit und die damit verbundenen Assets.
**Admin / Professional Extension:** Extension: Security Controls, Risk Assessment, Prevention, Detection, Response und Recovery als grundlegender Security-Lifecycle.
**Guided Practice:** Ein einfaches IT-System betrachten und Assets, mögliche Risiken und grundlegende Schutzmaßnahmen identifizieren.
**Independent Challenge:** Ein kleines Unternehmenssystem analysieren und die fünf wichtigsten Security-Risiken priorisieren.
**External Practice:** Eine grundlegende Security-Fundamentals-Übung durchführen.
**Verification:** IT-Security definieren, ihre Bedeutung erklären und mindestens drei grundlegende Security Controls nennen.

## 2 — Security: CIA Triad

**Theory:** Confidentiality, Integrity und Availability als zentrale Schutzziele der Informationssicherheit.
**Context / Why:** ie CIA Triad ermöglicht es, Sicherheitsanforderungen systematisch zu beschreiben und Security Incidents einzuordnen.
**Admin / Professional Extension:** Schutzmaßnahmen wie Access Control, Hashing, Encryption, Backups und Redundancy den jeweiligen CIA-Zielen zuordnen.
**Guided Practice:** Verschiedene Szenarien analysieren und bestimmen, ob Confidentiality, Integrity oder Availability betroffen ist.
**Independent Challenge:** Einen Security Incident analysieren und das verletzte CIA-Schutzziel sowie geeignete Gegenmaßnahmen bestimmen.
**External Practice:** CIA-Triad-Übung mit realistischen Security-Szenarien durchführen.
**Verification:** Confidentiality, Integrity und Availability erklären und jeweils ein praktisches Beispiel nennen.

## 3 — Security: Security Roles

**Theory:** User, Administrator, Auditor und Attacker sowie ihre unterschiedlichen Rollen und Verantwortlichkeiten.
**Context / Why:** Security benötigt klar definierte Verantwortlichkeiten und kontrollierte Zugriffsrechte.
**Admin / Professional Extension:** Least Privilege, Separation of Duties und Role-Based Access Control.
**Guided Practice:** Rollen und Berechtigungen für ein Beispielsystem definieren.
**Independent Challenge:** Eine fehlerhafte Rollen- und Berechtigungsstruktur analysieren und Sicherheitsprobleme identifizieren.
**External Practice:** Role-Based-Access-Control-Übung durchführen.
**Verification:** Security-Rollen unterscheiden und erklären, warum unterschiedliche Verantwortlichkeiten wichtig sind.

## 4 — Security: Attack Objectives

**Theory:** Typische Angriffsziele wie Datenklau, Sabotage, Erpressung und Identitätsdiebstahl.
**Context / Why:** Das Angriffsziel bestimmt häufig die Vorgehensweise des Angreifers und den potenziellen Schaden.
**Admin / Professional Extension:** Assets, Threats, Impact und Risk miteinander verbinden.
**Guided Practice:** Verschiedene Angriffsszenarien nach ihrem primären Ziel klassifizieren.
**Independent Challenge:** Für ein Unternehmenssystem die wahrscheinlichsten Angriffsziele identifizieren und priorisieren.
**External Practice:** Defensive Threat-Analysis-Übung durchführen.
**Verification:** Mindestens vier typische Angriffsmotive erklären und einem Beispiel zuordnen.

## 5 — Python: Secure Coding Basics

**Theory:** Grundlagen des sicheren Programmierens, sichere Eingaben, sichere Defaults und kontrollierte Fehlerbehandlung.
**Context / Why:** Unsichere Software kann selbst bei technisch sicheren Systemen neue Angriffsflächen erzeugen.
**Admin / Professional Extension:** Input Validation, Least Privilege, Dependency Security und sichere Fehlerbehandlung.
**Guided Practice:** Ein kleines Python-Programm mit validierter Benutzereingabe erstellen.
**Independent Challenge:** Unsichere Eingabeverarbeitung erkennen und den Code sicherer gestalten.
**External Practice:** Eine Secure-Coding-Python-Übung durchführen.
**Verification:** Mindestens drei Secure-Coding-Prinzipien erklären und praktisch anwenden.

## 6 — Git: Security Fundamentals

**Theory:** Source Code, Repository-Integrität und grundlegende Security-Anforderungen in Git.
**Context / Why:** Source Code kann sensible Informationen und sicherheitskritische Konfiguration enthalten.
**Admin / Professional Extension:** Secrets, Credentials, Repository Access und Commit Integrity.
**Guided Practice:** Ein Repository erstellen und einen sicheren Commit-Workflow durchführen.
**Independent Challenge:** Ein Repository auf versehentlich gespeicherte sensible Informationen untersuchen und geeignete Maßnahmen bestimmen.
**External Practice:** Git-Security-Übung durchführen.
**Verification:** Erklären, warum Credentials, API Keys und Secrets nicht in ein Repository gehören.

## 7 — Docker: Container Security Basics

**Theory:** Container, Images, Isolation und grundlegende Container-Security.
**Context / Why:** Container teilen sich den Kernel des Hosts und benötigen deshalb geeignete Isolation und Zugriffskontrollen.
**Admin / Professional Extension:**: Non-Root-Container, minimale Images, Capabilities und reduzierte Attack Surface.
**Guided Practice:** Einen Container untersuchen und feststellen, unter welchem User und mit welchen Rechten er läuft.
**Independent Challenge:** Eine unsichere Container-Konfiguration analysieren und mindestens drei Verbesserungen durchführen.
**External Practice:** Container-Security-Lab durchführen.
**Verification:** Container-Isolation erklären und wichtige grundlegende Security Controls nennen.

## 8 — Kubernetes: Security Overview

**Theory:** Kubernetes Security auf Cluster-, Node-, Pod- und Application-Ebene.
**Context / Why:** Kubernetes verteilt Workloads über mehrere Systeme und benötigt deshalb mehrere Security-Schichten.
**Admin / Professional Extension:** Authentication, Authorization, RBAC, Secrets und Network Policies.
**Guided Practice:** Einen Kubernetes-Pod untersuchen und sicherheitsrelevante Konfigurationen identifizieren.
**Independent Challenge:** Eine unsichere Pod-Konfiguration analysieren und Verbesserungen vorschlagen.
**External Practice:** Kubernetes-Security-Lab durchführen.
**Verification:** Die wichtigsten Security-Schichten eines Kubernetes-Clusters erklären.

## 9 — AI: Security Fundamentals

**Theory:** Security-Risiken bei AI-Systemen, Modellen, Daten und APIs.
**Context / Why:** AI-Systeme verarbeiten häufig sensible Daten und kommunizieren über externe Schnittstellen.
**Admin / Professional Extension:** Data Leakage, Access Control, API Security und sichere Datenverarbeitung.
**Guided Practice:** Einen einfachen AI-Workflow analysieren und seine Assets und Risiken identifizieren.
**Independent Challenge:** Ein AI-System anhand von Assets, Threats und Security Controls bewerten.
**External Practice:** Eine grundlegende AI-Security-Übung durchführen.
**Verification:** Mindestens vier grundlegende Security-Risiken eines AI-Systems erklären.

# 🛡️ DAY 2 — THREATS & ATTACKERS DAY

## 1 — Security: Threats

**Guided Practice:** Ein vereinfachtes Incident-Szenario anhand vorhandener Indikatoren untersuchen.

**Admin / Professional Extension:** Allowlisting, Type Validation, Boundary Checking und sichere Fehlerbehandlung.

## 6 — Git: Credential Protection

**Theory:** Credentials, Tokens und API Keys sind sensible Informationen und müssen geschützt werden.
**Context / Why:** Ein öffentlich gewordenes Credential kann direkten Zugriff auf Systeme und Daten ermöglichen.

## 7 — Docker: Trusted Images

# 🛡️ Day 3 — Cryptography Fundamentals

## LU 1 — Hash Functions

**Theory:** Hash Functions erzeugen aus Daten einen festen Hashwert und werden insbesondere für Integritätsprüfungen und Passwortschutz eingesetzt.
**Context / Why:** Bereits eine kleine Änderung an den Eingangsdaten erzeugt typischerweise einen anderen Hashwert und macht Manipulationen erkennbar.
**Admin / Professional Extension:** Sichere Hashverfahren wie SHA-256 von veralteten oder unsicheren Verfahren unterscheiden und Hashing nicht mit Verschlüsselung verwechseln.
**Guided Practice:** Dateien mit einer SHA-256-Hashfunktion prüfen und die erzeugten Hashwerte vergleichen.
**Independent Challenge:** Eine absichtlich veränderte Datei erkennen, indem ihr Hashwert mit einem bekannten Referenzwert verglichen wird.
**External Practice:** Eine praktische Hash- und Integritätsübung durchführen.
**Verification:** Hashing erklären, den Zweck eines Hashwerts beschreiben und eine Integritätsprüfung durchführen können.

## LU 2 — Symmetric Encryption

**Theory:** Symmetrische Verschlüsselung verwendet denselben geheimen Schlüssel zum Ver- und Entschlüsseln von Daten.
**Context / Why:** Sie ermöglicht effiziente Verschlüsselung großer Datenmengen, setzt aber eine sichere Schlüsselverteilung voraus.
**Admin / Professional Extension:** Geeignete moderne Verfahren wie AES erkennen und Schlüssel sicher verwalten.
**Guided Practice:** Daten mit einem symmetrischen Verschlüsselungsverfahren verschlüsseln und anschließend wieder entschlüsseln.
**Independent Challenge:** Einen sicheren Anwendungsfall für symmetrische Verschlüsselung auswählen und die notwendigen Schutzmaßnahmen bestimmen.
**External Practice:** Eine Symmetric-Encryption-Lab-Übung durchführen.
**Verification:** Symmetrische Verschlüsselung erklären und ihre Vorteile sowie zentrale Herausforderung nennen können.

## LU 3 — Asymmetric Encryption

**Theory:** Asymmetrische Kryptografie verwendet ein Schlüsselpaar aus Public Key und Private Key für Verschlüsselung, Authentifizierung und digitale Signaturen.
**Context / Why:** Sie ermöglicht sichere Kommunikation ohne vorherige gemeinsame Übertragung eines geheimen Schlüssels.
**Admin / Professional Extension:** Public und Private Keys korrekt unterscheiden und deren Schutzanforderungen erklären.
**Guided Practice:** Ein Schlüsselpaar erzeugen und die Funktionen von Public und Private Key untersuchen.
**Independent Challenge:** Für ein Kommunikationsszenario entscheiden, welcher Schlüssel für Verschlüsselung beziehungsweise Signatur verwendet wird.
**External Practice:** Eine Public-Key-Kryptografie-Übung durchführen.
**Verification:** Public Key, Private Key und die grundlegende Funktionsweise asymmetrischer Kryptografie erklären können.

## LU 4 — Encryption Use Cases

**Theory:** Verschlüsselung schützt Daten während der Übertragung und bei der Speicherung vor unbefugtem Zugriff.
**Context / Why:** Unterschiedliche Bedrohungssituationen erfordern unterschiedliche Verschlüsselungskonzepte.
**Admin / Professional Extension:** Data-at-Rest, Data-in-Transit und Ende-zu-Ende-Verschlüsselung unterscheiden und geeignete Controls auswählen.
**Guided Practice:** Verschiedene Szenarien analysieren und passende Verschlüsselungsverfahren zuordnen.
**Independent Challenge:** Ein kleines Unternehmenssystem analysieren und feststellen, welche Daten verschlüsselt werden müssen.
**External Practice:** Eine Encryption-Use-Case-Übung durchführen.
**Verification:** Mindestens drei praktische Einsatzbereiche von Verschlüsselung erklären und unterscheiden können.

## LU 5 — Python: Hashing

**Theory:** Python stellt Bibliotheken bereit, mit denen kryptografische Hashwerte für Daten erzeugt werden können.
**Context / Why:** Hashing ermöglicht beispielsweise Integritätsprüfungen und sichere technische Vergleichswerte.
**Admin / Professional Extension:** Sichere Hashalgorithmen verwenden und Hashing nicht als Ersatz für Verschlüsselung einsetzen.
**Guided Practice:** Ein Python-Skript erstellen, das den SHA-256-Hash einer Datei berechnet.
**Independent Challenge:** Ein Skript entwickeln, das Veränderungen an einer Datei anhand ihres Hashwerts erkennt.
**External Practice:** Eine Python-Hashing-Übung durchführen.
**Verification:** Einen SHA-256-Hash in Python erzeugen und seine sicherheitstechnische Bedeutung erklären können.

## LU 6 — Git: Hashes & Integrity

**Theory:** Git verwendet Hashwerte zur Identifikation und Integritätsprüfung von Objekten innerhalb eines Repositorys.
**Context / Why:** Hash-basierte Identifikation unterstützt die Erkennung unbeabsichtigter Veränderungen im Repository.
**Admin / Professional Extension:** Commit-Integrität, Repository-Objekte und kryptografische Hashes im Git-Kontext unterscheiden.
**Guided Practice:** Git-Commits untersuchen und deren Hashwerte nachvollziehen.
**Independent Challenge:** Änderungen zwischen zwei Commit-Zuständen analysieren und ihre Integrität bewerten.
**External Practice:** Eine Git-Integrity-Übung durchführen.
**Verification:** Erklären können, welche Rolle Hashes bei der Integrität von Git spielen.

## LU 7 — Docker: Image Integrity

**Theory:** Docker Images bestehen aus Layers und können anhand von Digests eindeutig referenziert werden.
**Context / Why:** Manipulierte Images können kompromittierte Software direkt in Produktionsumgebungen bringen.
**Admin / Professional Extension:** Image Digests, vertrauenswürdige Registries, Signing und Vulnerability Scanning berücksichtigen.
**Guided Practice:** Ein Docker Image untersuchen und seinen Digest bestimmen.
**Independent Challenge:** Ein Image anhand von Quelle, Tag, Digest und Scan-Ergebnis sicherheitstechnisch bewerten.
**External Practice:** Eine Docker-Image-Integrity-Übung durchführen.
**Verification:** Image Tag und Digest unterscheiden und erklären können, warum Integrität wichtig ist.

## LU 8 — Kubernetes: Secret Protection

**Theory:** Kubernetes Secrets dienen zur Verwaltung sensibler Werte wie Passwörter, Tokens und Schlüssel.
**Context / Why:** Unzureichend geschützte Secrets können zu unbefugtem Zugriff auf Anwendungen und Infrastruktur führen.
**Admin / Professional Extension:** RBAC, Secret Access, Encryption at Rest und sichere Secret-Verteilung berücksichtigen.
**Guided Practice:** Ein Kubernetes Secret erstellen und den Zugriff darauf kontrollieren.
**Independent Challenge:** Eine unsichere Secret-Konfiguration analysieren und geeignete Schutzmaßnahmen bestimmen.
**External Practice:** Ein Kubernetes-Secret-Security-Lab durchführen.
**Verification:** Erklären können, warum Kubernetes Secrets besonders geschützt und restriktiv zugänglich sein müssen.

## LU 9 — AI: Data Protection

**Theory:** AI-Systeme verarbeiten häufig Trainingsdaten, Prompts, Dateien und API-Daten mit potenziell sensiblen Informationen.
**Context / Why:** Unzureichender Datenschutz kann zu Data Leakage oder unerlaubter Weitergabe vertraulicher Informationen führen.
**Admin / Professional Extension:** Data Classification, Access Control, Encryption und Data Minimization einsetzen.
**Guided Practice:** Einen AI-Workflow analysieren und sensible Datenflüsse identifizieren.
**Independent Challenge:** Schutzmaßnahmen für einen AI-Service mit vertraulichen Unternehmensdaten entwerfen.
**External Practice:** Eine AI-Data-Protection-Übung durchführen.
**Verification:** Mindestens vier Maßnahmen zum Schutz sensibler AI-Daten erklären können.

# 🛡️ Day 4 — Key Management

## LU 1 — Keys

**Theory:** Kryptografische Schlüssel steuern Verschlüsselungs-, Entschlüsselungs- und Signaturvorgänge.
**Context / Why:** Die Sicherheit eines kryptografischen Systems hängt wesentlich vom sicheren Umgang mit seinen Schlüsseln ab.
**Admin / Professional Extension:** Key Generation, Storage, Rotation, Revocation und Destruction als Lifecycle betrachten.
**Guided Practice:** Verschiedene Schlüsselarten und ihre jeweiligen Verwendungszwecke dokumentieren.
**Independent Challenge:** Eine fehlerhafte Schlüsselverwaltung analysieren und Risiken identifizieren.
**External Practice:** Eine Key-Management-Grundlagenübung durchführen.
**Verification:** Kryptografische Schlüssel erklären und die wichtigsten Phasen ihres Lifecycles nennen können.

## LU 2 — Key Exchange

**Theory:** Key Exchange ermöglicht es Kommunikationspartnern, einen gemeinsamen geheimen Schlüssel sicher zu etablieren.
**Context / Why:** Ein geheimer Schlüssel darf nicht einfach ungeschützt über ein unsicheres Netzwerk übertragen werden.
**Admin / Professional Extension:** Verfahren wie Diffie-Hellman und deren Absicherung gegen Man-in-the-Middle-Angriffe verstehen.
**Guided Practice:** Einen vereinfachten Key-Exchange-Ablauf nachvollziehen.
**Independent Challenge:** Einen unsicheren Schlüsselaustausch analysieren und die Schwachstelle identifizieren.
**External Practice:** Eine Key-Exchange-Simulation durchführen.
**Verification:** Zweck und grundlegendes Prinzip eines sicheren Key Exchange erklären können.

## LU 3 — Perfect Forward Secrecy

**Theory:** Perfect Forward Secrecy stellt sicher, dass kompromittierte langfristige Schlüssel nicht automatisch vergangene Sitzungen entschlüsseln.
**Context / Why:** Dadurch bleibt vergangene Kommunikation auch nach einer späteren Schlüsselkompromittierung besser geschützt.
**Admin / Professional Extension:** Ephemeral Keys und moderne TLS-Key-Exchange-Verfahren einordnen.
**Guided Practice:** Einen Kommunikationsablauf mit und ohne Forward Secrecy vergleichen.
**Independent Challenge:** Die Auswirkungen eines kompromittierten langfristigen Private Keys auf vergangene Sessions bewerten.
**External Practice:** Eine PFS-Lernübung durchführen.
**Verification:** Perfect Forward Secrecy definieren und ihren Sicherheitsnutzen erklären können.

## LU 4 — Key Management

**Theory:** Key Management umfasst Erzeugung, Speicherung, Nutzung, Rotation, Verteilung und Widerruf kryptografischer Schlüssel.
**Context / Why:** Selbst starke Kryptografie verliert ihre Schutzwirkung bei unsicherer Schlüsselverwaltung.
**Admin / Professional Extension:** Least Privilege, Key Rotation, HSM/KMS-Konzepte und Zugriffskontrollen berücksichtigen.
**Guided Practice:** Einen einfachen Key-Lifecycle dokumentieren.
**Independent Challenge:** Eine fehlerhafte Key-Management-Architektur analysieren und verbessern.
**External Practice:** Eine Key-Management-Lab-Übung durchführen.
**Verification:** Die wichtigsten Phasen eines Key Lifecycles erklären und geeignete Controls nennen können.

## LU 5 — Python: Key Handling

**Theory:** Kryptografische Schlüssel müssen in Anwendungen sicher erzeugt, verarbeitet und gespeichert werden.
**Context / Why:** Hartcodierte oder ungeschützte Schlüssel können zu vollständiger Kompromittierung geschützter Daten führen.
**Admin / Professional Extension:** Secret Stores, Umgebungsvariablen, Berechtigungen und sichere Bibliotheken verwenden.
**Guided Practice:** Einen Schlüssel in Python sicher aus einer externen Konfiguration beziehen.
**Independent Challenge:** Hartcodierte Secrets aus einem Beispielprogramm entfernen und durch eine sichere Lösung ersetzen.
**External Practice:** Eine Python-Key-Handling-Übung durchführen.
**Verification:** Mindestens drei sichere Regeln für den Umgang mit Keys in Python erklären können.

## LU 6 — Git: Signing

**Theory:** Git kann Commits und Tags kryptografisch signieren, um deren Urheberschaft und Integrität besser nachvollziehbar zu machen.
**Context / Why:** Signaturen helfen dabei, vertrauenswürdige Änderungen von manipulierten oder nicht verifizierten Änderungen zu unterscheiden.
**Admin / Professional Extension:** GPG/SSH-Signing, Signaturprüfung und Trust Models berücksichtigen.
**Guided Practice:** Einen signierten Git-Commit erzeugen und anschließend verifizieren.
**Independent Challenge:** Einen Repository-Verlauf auf signierte und nicht signierte Commits untersuchen.
**External Practice:** Eine Git-Signing-Übung durchführen.
**Verification:** Zweck digital signierter Git-Commits erklären und eine Signatur prüfen können.

## LU 7 — Docker: Key/Secret Handling

**Theory:** Container benötigen gelegentlich Passwörter, Tokens oder Zertifikate, die nicht Bestandteil des Images sein dürfen.
**Context / Why:** In Images gespeicherte Secrets können durch Layer oder Registry-Zugriff dauerhaft offengelegt werden.
**Admin / Professional Extension:** Secret Injection, Runtime Secrets und minimale Berechtigungen einsetzen.
**Guided Practice:** Ein Container-Setup untersuchen und gespeicherte Secrets identifizieren.
**Independent Challenge:** Eine unsichere Docker-Konfiguration ohne Secrets im Image neu gestalten.
**External Practice:** Eine Container-Secret-Management-Übung durchführen.
**Verification:** Erklären können, warum Secrets nicht in Dockerfiles oder Images eingebettet werden sollten.
